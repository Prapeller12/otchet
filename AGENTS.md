# Руководство Codex по разработке системы производственной отчётности

Версия: 1.0  
Дата: 30.08.2026  
Статус: обязательная инструкция для разработки

## 1. Назначение файла

Этот файл задаёт обязательные правила для Codex и других разработчиков, работающих с репозиторием системы автоматизации и централизации производственной отчётности.

Codex обязан прочитать этот файл полностью перед анализом задачи, составлением плана, изменением архитектуры, кода, схемы БД, интерфейса, импорта, экспорта или сборки.

Главный источник требований — актуальная утверждённая DEV-документация проекта. Настоящий файл переводит её положения в рабочие правила разработки. При обнаружении противоречия Codex должен остановить затронутую часть работы, описать противоречие и запросить решение владельца программы.

## 2. Иерархия источников требований

Приоритет документов и решений, от высшего к низшему:

1. Прямое последнее указание владельца программы.
2. Подтверждённые принципы актуальной DEV-документации.
3. Настоящий `AGENTS.md`.
4. Утверждённые эталонные Excel-файлы и изображения отчётных форм.
5. Спецификации API, БД, импорта, frontend и тестирования в папке `docs/`.
6. Существующий код и комментарии.
7. Предположения Codex.

Предположение никогда не может отменять утверждённое требование. Если данных недостаточно, использовать явный `TODO/OPEN`, а не придумывать бизнес-правило.

## 3. Цель программы

Программа должна заменить разрозненное хранение, ручное сведение и пересылку Excel-файлов единым контуром:

- ввода первичных производственных данных;
- проверки и согласования;
- расчёта плана/факта, остатков, дефицита и комплектности;
- хранения истории и бизнес-аудита;
- формирования отчётов в привычной форме;
- перехода от локальной версии к централизованной многопользовательской версии.

Программа автоматизирует хранение и расчёты, но не переучивает пользователей и не изменяет привычную структуру заполнения отчётов.

## 4. Неизменяемые принципы

Следующие правила запрещено менять без отдельного письменного решения владельца программы.

### 4.1. Поставка и запуск

- Программа поставляется ZIP-архивом.
- Установка, MSI/NSIS/Inno Setup, службы, автозапуск и права администратора не требуются.
- На целевом компьютере не требуется отдельно устанавливать Python, Node.js, браузер или runtime.
- Не упаковывать весь проект в один EXE.
- Использовать раздельную `onedir`-структуру: launcher, backend, frontend, runtime, config, resources, data, migrations и документация находятся в отдельных папках.
- Не использовать PyInstaller `onefile`.
- Не размещать рабочую SQLite на сетевом/UNC-диске для совместной работы.

### 4.2. Структура отчётных форм

- Интерфейс ввода должен строго соответствовать утверждённым Excel-формам.
- Даты остаются горизонтальными колонками слева направо.
- Изготовители, поставщики, изделия, сборочные комплекты, ДСЕ и ПКИ остаются вертикальными группами.
- Строки `план`, `факт`, `получено`, `использовано`, `остаток`, `выпуск`, `отправка` и `прибытие` сохраняют исходный порядок.
- Основной ввод выполняется непосредственно в разрешённых ячейках матрицы.
- Нельзя заменять матричный ввод карточками, Kanban-доской, календарём или отдельным мастером для каждого значения.
- Нельзя скрывать обязательные строки, нулевые дни или позиции по умолчанию.
- Пустая ячейка означает «данные не представлены»; числовой ноль означает подтверждённое отсутствие количества. Эти состояния различаются в UI, API и БД.
- Расчётные значения не редактируются вручную.
- Сводки, графики и списки отклонений разрешены только как дополнительные представления чтения.

### 4.3. Данные и расчёты

- Первичные операции хранятся отдельно от итоговых показателей.
- Остаток, потребность, дефицит, процент выполнения и готовые комплекты рассчитываются backend.
- Проведённая операция не удаляется. Исправление выполняется сторно и новой операцией с причиной.
- Импорт не изменяет рабочие данные до проверки и подтверждения.
- Повторный импорт одного источника не создаёт дубли.
- BOM и другие нормативы версионируются и имеют период действия.
- Закрытый период нельзя редактировать обычному оператору.
- Константы, справочники, роли, пороги, шаблоны и нормы нельзя зашивать в программный код.

### 4.4. Логи и следы запуска

- Собственные текстовые debug/access-логи по умолчанию выключены.
- Телеметрия и внешние сетевые обращения в локальном режиме отсутствуют.
- Бизнес-аудит внутри БД обязателен и не считается техническим логом.
- Нельзя обещать полностью бесследный запуск: Windows, NTFS, Defender/EDR, WebView2 и SQLite могут создавать независимые технические следы.
- Codex не должен разрабатывать функции удаления системных журналов Windows или следов защитного ПО.

## 5. Канонические формы frontend

### 5.1. Ежедневное движение и остатки

Сохранять следующую матрицу:

- левая группа: изготовитель/поставщик и позиция;
- строки позиции: `Получено` → `Использовано` → `Остаток`;
- строки сборочного комплекта: `План выпуска` → `Выпущено по кодам` → `Отправка` → `Прибытие`;
- строки готового изделия: `План выпуска` → `Выпущено по кодам` → `Отправка` → `Прибытие`;
- нижний блок: склад по кодам/модификациям и готовые комплекты;
- горизонтальная ось: календарные даты месяца;
- итоговые показатели располагаются рядом с исходной формой.

### 5.2. Головная площадка

Сохранять:

- изготовитель/поставщик → сборочный комплект;
- изготовитель/поставщик → готовое изделие;
- план выпуска перед фактом выпуска;
- разбивку по кодам/модификациям;
- даты месяца по горизонтали;
- сводный блок `всего получено`, `всего использовано`, `остаток изделий`;
- месячные и накопительные итоги.

### 5.3. Дочерние общества

Сохранять:

- изготовитель/поставщик → изделие/ДСЕ/ПКИ;
- договорной или годовой объём;
- утверждённый план;
- недели или даты периода по горизонтали;
- поставку накопительно;
- отклонение и профицит/дефицит.

### 5.4. Поведение таблиц

- Закреплять верхнюю строку дат и левые идентификационные колонки.
- Поддерживать навигацию стрелками, `Enter` и `Tab`.
- Поддерживать вставку прямоугольного диапазона из Excel с предварительной проверкой.
- Числа выравнивать вправо и отображать с единым форматом точности.
- Вводимые, расчётные, заблокированные и ошибочные ячейки должны различаться не только цветом, но и текстом/иконкой/состоянием.
- После изменения показывать несохранённое состояние до подтверждения backend.
- Боковая расшифровка допустима, но не должна заменять матрицу или сбрасывать положение пользователя.
- При любом изменении структуры формы нужен протокол различий с эталоном.

## 6. Бизнес-логика

### 6.1. Остаток

```text
stock(component, date) = opening_balance
  + receipts
  + production_receipts
  + returns
  - consumption
  - shipments
  - write_offs
  + signed_adjustments
```

Каждое слагаемое агрегируется из отдельных проведённых операций до выбранной даты включительно.

### 6.2. Потребность

```text
required_qty = product_plan_qty × qty_per_product × (1 + loss_factor)
```

`loss_factor` хранится в конфигурации или версии BOM. До утверждения иного правила значение по умолчанию равно нулю.

### 6.3. Готовые комплекты

```text
available_sets_i = floor(available_qty_i / qty_per_product_i)
ready_sets = min(available_sets_i) по всем обязательным компонентам
```

При одинаковом минимуме вернуть все ограничивающие позиции.

Контрольный пример:

```text
остаток = 71
входимость = 3
готовые комплекты = floor(71 / 3) = 23
```

### 6.4. Дефицит

```text
shortage_to_target = max(0, target_sets × qty_per_product - available_qty)
contract_variance = supplied_qty_to_date - contract_planned_qty_to_date
```

Отрицательное договорное отклонение — дефицит, положительное — профицит.

### 6.5. План/факт

```text
completion_rate = fact_qty / plan_qty × 100%
```

Если `plan_qty = 0`, процент не рассчитывается. Возвращать `NOT_APPLICABLE`, а не 0% или 100%.

## 7. Архитектурная граница

Использовать слоистую архитектуру:

```text
frontend
  ↓ типизированный application-контракт
application / use cases
  ↓
domain
  ↓
repositories
  ↓
SQLite или PostgreSQL
```

Запрещено:

- обращаться к SQLite напрямую из React;
- размещать бизнес-формулы только во frontend;
- смешивать HTTP/IPC, SQL и доменную логику в одном модуле;
- привязывать доменные сервисы к конкретному UI;
- дублировать формулы в UI, экспорте и backend;
- использовать Excel-адрес ячейки как постоянный идентификатор бизнес-данных.

Frontend-ячейка адресуется устойчивыми координатами:

```text
report_type
organization_id
product_id или component_id
metric_code или operation_type
operation_date или period_start
bom_version_id, если влияет на расчёт
```

## 8. Базовый технологический стек

Текущий базовый вариант:

- Python 3.12;
- PyWebView;
- React + TypeScript + Vite, статическая SPA-сборка;
- SQLite для локального MVP;
- PostgreSQL и REST API для централизованного режима;
- WebView2 Fixed Runtime внутри ZIP;
- pytest для backend;
- Vitest/Testing Library для frontend;
- Playwright для критических пользовательских сценариев, если он включён в dev-контур.

Замена языка, фреймворка, WebView, БД или способа упаковки требует отдельного ADR с сравнением рисков, размера поставки, автономности и совместимости с Windows 10/11.

## 11. Модель данных

Минимальные доменные группы таблиц:

- `organizations`;
- `users`, `roles`, `user_roles`;
- `products`, `components`;
- `bom_versions`, `bom_items`;
- `suppliers`, `supply_contracts`;
- `production_plans`, `supply_plans`;
- `stock_operations`, `product_operations`;
- `periods`, `period_closures`;
- `readiness_snapshots` — только аудиторские снимки, не первичный источник;
- `import_batches`, `import_rows`, `import_errors`;
- `audit_events`.

Обязательные правила:

- первичные ключи не зависят от номера строки Excel;
- количество хранится точным числовым типом, не `float`;
- дата операции и время создания записи — разные поля;
- каждая бизнес-таблица в централизованном режиме имеет область `organization_id`;
- миграции только последовательные и версионируемые;
- изменение применённой миграции запрещено — добавлять новую;
- все внешние ключи, уникальности и check-ограничения определять явно;
- удаление проведённых операций запрещено ограничениями сервиса и тестами.

## 12. Backend API

Префикс централизованного API: `/api/v1`.

Минимальные группы маршрутов:

```text
GET/POST  /organizations
GET/POST  /products
GET/POST  /components
GET/POST  /products/{id}/bom/versions
POST      /bom/{id}/approve
GET/POST  /plans/production
GET/POST  /plans/supply
POST      /operations/stock
POST      /operations/products
POST      /operations/{id}/reverse
GET       /stock/balances
GET       /reports/readiness
GET       /reports/shortages
GET       /reports/head-site
GET       /reports/subsidiary
GET       /reports/daily
GET       /reports/summary
POST      /imports
GET       /imports/{id}/preview
POST      /imports/{id}/commit
POST      /periods/{id}/close
POST      /exports
```

Общие правила:

- даты передаются в ISO 8601;
- количества передаются без потери точности;
- списки имеют пагинацию, сортировку и фильтры;
- создающие запросы поддерживают `idempotency-key`;
- ошибки имеют единый формат `code`, `message`, `field_errors`, `request_id`;
- API не возвращает произвольный 0 вместо отсутствующего значения;
- права и `organization_id` проверяются backend, а не только UI;
- локальный IPC/bridge и REST используют одни application-сервисы.

## 13. Импорт Excel

Импорт выполняется конвейером:

1. Выбор типа шаблона.
2. Копирование во временную область приложения.
3. Вычисление SHA-256.
4. Разбор в staging.
5. Проверка справочников, дат, чисел, дублей и структуры.
6. Формирование предпросмотра `NEW / CHANGED / SAME / ERROR`.
7. Подтверждение пользователем.
8. Резервная копия перед изменением.
9. Проведение одной транзакцией.
10. Фиксация пакета импорта и итоговых счётчиков.

Критическая ошибка откатывает весь пакет. Codex не должен автоматически угадывать изделие, поставщика или компонент при неоднозначном сопоставлении.

Для каждого шаблона создать отдельную спецификацию:

- имя и назначение листа;
- обязательные строки и колонки;
- объединённые ячейки;
- тип каждой вводимой ячейки;
- вычисляемые поля;
- устойчивый бизнес-ключ;
- правила пустых значений и нулей;
- контрольные примеры;
- экспортное соответствие.

## 14. Экспорт

- Экспорт строится из БД, а не копированием текущего DOM.
- Результат должен повторять утверждённую Excel-форму.
- Шаблоны находятся в `resources/templates`.
- Значения и формулы экспорта должны быть прозрачными и проверяемыми.
- Текущие фильтры и период включаются в параметры экспорта.
- Экспорт не должен включать скрытые технические поля, пароли, токены и внутренние идентификаторы без необходимости.

## 15. Роли и права

Базовые роли:

- наблюдатель;
- оператор дочернего общества;
- оператор головной площадки;
- планировщик;
- контролёр;
- администратор.

Codex не должен расширять права роли только ради упрощения интерфейса. Каждая команда backend проверяет роль, организацию, период и состояние объекта.

## 16. Порядок работы Codex

Перед каждой задачей Codex обязан:

1. Прочитать `AGENTS.md` и релевантные документы из `docs/`.
2. Проверить состояние репозитория и не затереть пользовательские изменения.
3. Сформулировать ожидаемый результат и критерии приёмки.
4. Определить, затрагивает ли задача утверждённые формы, расчёты, БД, API или упаковку.
5. При архитектурном изменении подготовить ADR до реализации.
6. Разбить работу на небольшие проверяемые этапы.
7. Реализовать изменение в правильном слое.
8. Добавить или обновить тесты.
9. Запустить релевантные проверки.
10. Обновить документацию и сообщить о незакрытых рисках.

Codex не должен отвечать «готово», если код не собран или не проверен доступными тестами.

## 17. План реализации

Разрабатывать последовательно.

### Этап 0. Фиксация контрактов

- эталонные формы;
- словарь терминов;
- организации и подчинённость;
- коды изделий, ДСЕ и ПКИ;
- типы операций;
- роли и закрытие периода;
- правила нуля и пустого значения.

### Этап 1. Основа данных

- схема SQLite;
- миграции;
- репозитории;
- справочники;
- BOM;
- операции и сторно.

### Этап 2. Расчёты

- остатки;
- потребность;
- готовые комплекты;
- bottleneck;
- дефицит;
- план/факт.

### Этап 3. Канонический frontend

- оболочка приложения;
- три матричные формы;

## 18. Тестирование

Минимальный обязательный набор:

### Unit

- остаток по набору операций;
- сторно;
- потребность;
- готовые комплекты;
- несколько bottleneck;
- дефицит;
- нулевой план;
- пустое значение против нуля.

### Интеграционные тесты БД

- миграции на пустой и существующей БД;
- ограничения и внешние ключи;
- транзакции импорта;
- откат ошибки;
- закрытый период;
- разграничение организаций.

### Контрактные тесты API

- JSON-схемы;
- коды ошибок;
- идемпотентность;
- пагинация;
- права;
- точность количеств.

### Frontend

- соответствие порядка групп и строк эталону;

- клавиатурная навигация;
- вставка диапазона;

- сохранение положения при открытии расшифровки.

### Excel

- каждый утверждённый шаблон;

- неверные даты и числа;

- отсутствие собственных `.log` при стандартной настройке.

Контрольные расчётные значения из исходных материалов: 23 и 30 готовых комплектов в соответствующих контрольных сценариях.

## 19. Definition of Done

Задача считается завершённой только если:

- выполнены согласованные критерии приёмки;
- не нарушена структура канонических форм;
- бизнес-логика находится в backend/domain, а не продублирована во frontend;
- схема БД изменена миграцией;
- тесты добавлены и проходят;
- сборка соответствующего модуля проходит;
- статический анализ и форматирование проходят;
- ошибки и пустые состояния обработаны;
- права проверяются backend;
- документация обновлена;
- нет секретов и пользовательских данных в репозитории;
- Codex перечислил изменённые файлы, проверки, ограничения и открытые вопросы.

## 20. Обязательный формат отчёта Codex

После реализации Codex сообщает:

```text

- что реализовано;

Проверки
```

## 21. Запрещённые действия

Codex запрещено без отдельного указания:

- изменять парадигму заполнения отчётов;
- заменять матрицы Kanban-доской или карточками;
- менять порядок строк и дат;
- создавать один монолитный EXE;
- добавлять установщик;
- использовать внешний CDN, телеметрию или облачный сервис в локальном режиме;
- отключать безопасное журналирование транзакций SQLite;
- хранить пароли открытым текстом;
- помещать секреты в ZIP или Git;
- удалять проведённые операции;
- молча исправлять или угадывать импортированные данные;
- редактировать применённые миграции;
- делить общие бизнес-данные по независимым SQLite-файлам организаций;
- использовать общий SQLite-файл несколькими пользователями через сетевую папку;
- обещать отсутствие любых системных следов Windows;
- удалять или перезаписывать пользовательские файлы и изменения;
- выполнять разрушительные Git-команды без прямого разрешения;
- расширять задачу и внедрять неподтверждённые интеграции.

## 22. Управление изменениями

Для изменения утверждённого принципа создать ADR в `docs/decisions/`:

```text
ADR-XXXX: название решения
Статус: PROPOSED / ACCEPTED / REJECTED / SUPERSEDED
Дата
Причина
Текущее поведение
Предлагаемое изменение
Влияние на UI
Влияние на данные и миграции
Влияние на API
Влияние на portable-сборку
Риски
План отката
Необходимые тесты
Решение владельца
```

До статуса `ACCEPTED` изменение не считается утверждённым.

## 23. Открытые вопросы, которые нельзя решать догадкой

- полный перечень организаций и их подчинённость;
- точные коды изделий, модификаций, ДСЕ и ПКИ;
- утверждённые эталонные формы и нумерация строк/колонок;
- какие поля каждой формы вводятся, рассчитываются или импортируются;
- источник и дата каждого вида факта;
- правила закрытия и повторного открытия периода;
- состав бизнес-аудита и срок хранения;
- необходимость вложений и допустимые форматы;
- контракт интеграции с 1С;
- требования информационной безопасности;
- место размещения централизованного сервера;
- правила миграции из локальной версии.

Codex должен вынести такой вопрос на согласование, если он блокирует корректную реализацию. Временное решение допускается только как явно обозначенный placeholder без выдачи за утверждённую бизнес-логику.
